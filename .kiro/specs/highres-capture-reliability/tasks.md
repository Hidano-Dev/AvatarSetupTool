# Implementation Plan

- [ ] 1. テスト基盤を新設し現行挙動を固定する
- [x] 1.1 Editor テストアセンブリの新設と internal 公開
  - パッケージ内に EditMode テスト用のテストアセンブリ (Tests/Editor) を新設し、Test Runner 参照・nunit precompiled 参照・UNITY_INCLUDE_TESTS 制約・Editor 限定の定型構成で本体アセンブリを参照する
  - 本体アセンブリに InternalsVisibleTo を追加し、internal のロジックをテストから検証可能にする (埋め込みパッケージのため manifest 変更は不要)
  - 完了条件: Unity Test Runner (EditMode) にテストアセンブリが表示され、internal メンバを参照するプレースホルダテストがコンパイル・実行できる
  - _Requirements: 1.4, 3.1, 4.4, 4.5, 6.1_

- [x] 1.2 現行縮小合成と iTXt メタデータの挙動固定テスト
  - 現行のボックス平均縮小 (samples/2 加算の四捨五入) の出力を固定する基準テストを作成し、後続の置換における同値性比較の基準にする
  - iTXt 挿入の挙動 (IHDR 直後への挿入位置・CRC・UTF-8 本文のラウンドトリップ) を固定するテストを作成する
  - 完了条件: 両テストが現行実装に対してグリーンで、以後の変更による退行を検出できる状態になっている
  - _Requirements: 1.4, 4.5, 6.1_

- [ ] 2. タイル分割レイアウトと SSAA 決定を純粋ロジックとして一般化する
- [x] 2.1 タイル辺長の算出とタイルレイアウト計算の実装
  - 安全上限 4096px・maxTextureSize・VRAM 予算由来の辺長の最小値からレンダ辺長上限を算出する (graphicsMemorySize の過小報告対策として 1024MB の下限クランプを適用)
  - 出力解像度・SSAA 倍率・辺長上限から任意分割数の非一様タイルレイアウト (端タイルは剰余サイズ) を決定的に算出し、タイル矩形とタイル 1 枚の最大レンダピクセル数を提供する
  - 環境値は引数で受け取り Unity API を呼ばない純粋計算とし、全タイル矩形が出力全域を重複・欠落なく被覆しタイル境界が出力ピクセル境界に整列することを不変条件とする
  - 完了条件: 8K+SSAA×2 の入力で 4096px 級タイルの分割レイアウトが得られ、maxTextureSize と算出辺長のいずれも超えないレンダサイズのみが算出される
  - _Requirements: 1.1, 1.2, 1.3, 1.5_

- [ ] 2.2 SSAA 倍率決定ポリシーの組み込み
  - 解像度既定の倍率 (最長辺 2048px 以下は 4、超は 2) を常に採用し、VRAM 予算不足を理由とする降格は行わない (タイル分割が VRAM 制約を吸収する)
  - 辺長上限を倍率で割った値が最小ブロック辺 (64px) を下回る縮退時のみ段階的に倍率を下げ、要求倍率と適用倍率の両方をレイアウト結果に含めて呼び出し側が警告ログで可視化できるようにする
  - 完了条件: 通常環境では常に既定倍率が適用され、縮退入力でのみ要求/適用倍率の差分が結果に現れる
  - _Requirements: 2.1, 2.2, 2.3_

- [ ] 2.3 レイアウト計算の単体テスト
  - 境界ケースを網羅する: 8192×2 / 上限 4096 → 4×4 分割、非正方形、剰余タイルあり、上限以下 → 1×1 (単一パス)
  - 縮退条件での倍率降格と要求/適用倍率の報告を検証する
  - 被覆・非重複・境界整列・辺長上限遵守の不変条件をプロパティ的に検証する
  - 完了条件: 上記ケースを含む単体テストが EditMode で全てグリーン
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 2.1, 2.3_

- [ ] 3. タイル描画を一般化し黒フレーム失敗を検出・伝搬する
- [ ] 3.1 (P) 黒フレーム判定の実装と単体テスト
  - 読み戻したピクセル配列の全画素が RGB=(0,0,0) かを判定する純粋関数を実装する (アルファは無視、非黒画素の発見で早期終了)
  - 全黒 → 真、1 画素のみ非黒 (先頭/末尾/中間) → 偽、アルファのみ非ゼロの全黒 → 真のテストを作成する
  - 完了条件: 判定関数の単体テストが全てグリーン
  - _Requirements: 3.1_
  - _Boundary: 黒フレーム検出_
  - _Depends: 1.1_

- [ ] 3.2 タイル描画パイプラインの一般化
  - 静止画描画をレイアウト計算の結果 (非一様タイル矩形) に基づく分割描画へ置換し、旧来の 2 冪約数限定のタイル数決定と VRAM 予算による SSAA 降格ロジックを撤去する (この段階では合成先は現行の Color32[] のまま)
  - タイル矩形からカメラ矩形への換算 (orthoSize・中心座標) は double で計算してカメラ設定直前に float 化し、端の剰余タイルでもピクセル境界に正確に一致させる
  - タイル用テクスチャは各タイル処理後に即破棄し、同時生存を 1 枚に保つ
  - タイルループの各反復前に直前と同一の進捗テキスト・進捗値でキャンセル判定を追加し、進捗コールバック契約は不変のままキャンセル応答性を高める (キャンセル検出時は保存前に脱出し書きかけの PNG を残さない)
  - 完了条件: 単一パス (1×1) を含む任意分割で従来と同一の静止画が得られ、既存の挙動固定テストが退行しない
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.2, 6.3_

- [ ] 3.3 黒フレーム検出・リトライ・失敗伝搬の組み込み
  - タイル読み戻し直後 (合成前) に全画素黒を検査し、黒検出時は同一タイルを同一プレビューで 1 回だけ再描画・再検査する (リトライ発生時は警告ログにタイル座標を記録)
  - 再失敗時は構図/方向・出力解像度・SSAA 要求/適用倍率・タイル位置と総数・タイルのレンダサイズ・環境値 (maxTextureSize / graphicsMemorySize) を含む診断メッセージ付きの内部例外を PNG 保存前に送出する
  - キャプチャ入口で内部例外を捕捉してエラーログと失敗結果 (既存の Result 契約) へ変換し、UI ダイアログと CLI の戻り値・ログの双方で失敗を判別可能にする (公開契約は不変)
  - 完了条件: 描画失敗時に黒い PNG が一切保存されず、失敗が結果契約とログの両方で報告される
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 6.4, 6.5_

- [ ] 3.4 (P) タイル描画と単一パス描画の等価性統合テスト
  - 小サイズ (512px 級) で辺長上限を強制的に絞り、多タイル描画と単一パス描画の全ピクセルを比較する (EditMode で GPU 描画を直接使用)
  - 必須ケース: 剰余タイルを含む不均等分割、非正方形構図、非 2 冪の分割数 (例 3×2)
  - 完了条件: 完全一致、または差がある場合も各チャンネル ±1 階調以内で全ケース合格
  - _Requirements: 1.4_
  - _Boundary: RenderStill パイプライン (等価性テストのみ)_

- [ ] 3.5 (P) 黒フレーム失敗経路の統合テスト
  - テスト用フックで描画結果を全黒化し、リトライがちょうど 1 回行われることと再失敗時の内部例外送出を確認する
  - 失敗時に PNG ファイルが生成されないことを確認する
  - 完了条件: 失敗経路テストがグリーンで、黒 PNG 非生成が自動検証される
  - _Requirements: 3.2, 3.3_
  - _Boundary: 失敗伝搬 (テスト用フック追加を含む)_

- [ ] 4. PNG エンコードを省メモリ経路へ置換する
- [ ] 4.1 (P) 直接エンコードのピクセル一致・行順検証テスト
  - 乱数 + 背景色パターンの RGB24 バッファを直接エンコード API と現行の Texture2D 経路の両方で PNG 化し、デコード後のピクセル値完全一致を検証する (PNG バイト列自体は圧縮器差で異なってよい)
  - 最上段に置いたマーカー画素が PNG 先頭行に現れることで行順 (top-down 推定) を確定する。不一致の場合はフォーマット・行順の組合せを切り替えて確定する
  - 完了条件: 採用するフォーマットと行順が確定し、一致テストがグリーン (フェーズ 2 の入口ゲート)
  - _Requirements: 4.4, 6.1_
  - _Boundary: PNG エンコード経路 (テストのみ、製品コード変更なし)_
  - _Depends: 1.1_

- [ ] 4.2 RGB24 合成バッファ向け縮小合成ヘルパの実装
  - タイル読み戻し (ボトムアップ行順) をボックス平均で縮小し、RGB24 top-down 合成バッファの出力矩形へ行反転しながら書き込むヘルパを実装する (丸め式は現行と同一。行順・フォーマットは 4.1 の確定結果に追随するため並行実行不可)
  - 合成バッファからアニメ解像度へのボックス平均縮小 (GIF フレーム用、top-down → top-down) を実装する
  - タイル分割合成と単一縮小の全画素一致、および GIF フレームの現行同値性を検証するテストを作成する (1.2 の基準テストと突き合わせ)
  - 完了条件: 縮小合成の同値性テストが全てグリーン
  - _Requirements: 1.4, 4.1, 6.2_

- [ ] 4.3 静止画エンコード経路の置換と GIF フレーム共有の追随
  - 静止画の合成先を RGB24 (3 bytes/px)・top-down の byte[] へ変更し、Texture2D + SetPixels32 + EncodeToPNG を静止画経路から撤去して直接エンコードへ置換する
  - エンコード結果へ既存の iTXt 挿入を無変更で適用し、ファイル名規則・保存フローは変更しない
  - GIF フレーム生成を新バッファ形式からの縮小へ追随させ、動画経路 (MP4/ProRes) は無変更のまま維持する
  - エンコード結果が null/空の場合は防衛的に検出し、黒フレームと同経路で失敗報告して壊れたファイルを残さない
  - 完了条件: 全テスト (等価性・同値性・ピクセル一致・iTXt) がグリーンのまま、静止画が全面中間コピーを経由しない新経路で書き出される
  - _Requirements: 4.1, 4.2, 4.4, 4.5, 6.1, 6.2_

- [ ] 5. メモリ・時間見積もりを新経路へ整合させる
- [ ] 5.1 メモリ見積もりと撮影可否判定の更新
  - 静止画 1 枚のピーク算定を新経路の実バッファ構成 (RGB24 合成バッファ + タイル読み戻し ×2 + エンコード出力 + iTXt コピー) に基づいて改定する (GIF 蓄積分は現行式を維持、公開シグネチャは不変)
  - 撮影可否判定はレイアウト計算から得た実際の適用倍率・タイルサイズで算定して見積もりと実行を一致させ、出力レンダ解像度の maxTextureSize 超過チェックは現行どおり維持する
  - 8K/Both/GIF などの代表設定で「新見積もり ≤ 現行見積もり」かつ 8K がメモリ予算比較で誤拒否されないことを、環境値を引数化した内部関数のテストで確認する
  - 完了条件: 見積もり検証テストがグリーンで、新経路で撮影可能な設定が不足と誤判定されない
  - _Requirements: 2.2, 5.1, 5.2_

- [ ] 5.2 時間見積もり係数の更新
  - 静止画描画レートをタイルオーバーヘッド込みの実測で、PNG エンコードレートを新エンコード経路の実測値で再較正する (5.1 と同一の見積もり定数群を変更するため並行実行不可)
  - 所要時間見積もりの SSAA 倍率参照をレイアウト計算の適用倍率へ差し替える (残差は既存の較正係数の平滑化が吸収)
  - 完了条件: 所要時間見積もりが新経路の実測に基づく係数で算出される
  - _Requirements: 5.3_

- [ ] 6. 統合検証を行う
- [ ] 6.1 キャプチャ経路スモークテストと全テスト実行
  - 小型テストモデルでキャプチャを実行し、PNG が生成され iTXt が読めること、成功結果が返ることを EditMode テストで確認する
  - 全テストスイート (単体 + 統合) を実行し全件グリーンを確認する
  - 完了条件: Unity Test Runner (EditMode) で全テストが成功する
  - _Requirements: 6.1, 6.4_

- [ ] 6.2 8K 実機検証 (ピークメモリ・継ぎ目・SSAA 非降格・時間較正)
  - 8K / Both / ImagesOnly を実機撮影し、撮影直前に GC を発生させたベースラインと Profiler の Total Used Memory の撮影中ピークの差分で CPU 側ピークメモリを測定する (合格閾値: 1 枚あたり 1GB 未満。ベースライン・ピーク・差分を検証レポートに記録)
  - 実機 8K 出力に対しレイアウト計算から算出したタイル境界の行・列を境界を跨いで比較し、継ぎ目起因の段差がないこと (差がある場合も各チャンネル ±1 階調以内) を確認して記録する
  - 低 VRAM 環境 (または graphicsMemorySize の擬似低値) で 8K 撮影が SSAA 降格なしに完了することを確認する
  - 撮影後の時間見積もり誤差が較正係数の更新で収束することを確認する
  - 完了条件: 全項目が合格閾値を満たし、実測値が検証レポートに記録されている
  - _Requirements: 1.4, 2.2, 4.2, 5.3_

## 対象外要件の記録

- **4.3**: 「行バンド単位のストリーミング PNG エンコーダを採用する場合 (Where 句)」の条件付き要件。設計で Option 4-A (RGB24 byte[] の直接エンコード) を採用したため本計画では発火せず、対応タスクは設けない。4-A でピーク削減目標 (4.2) を満たせない場合のみ、予備フェーズ 4-B として別途設計・計画する (design.md「Migration Strategy」参照)。
